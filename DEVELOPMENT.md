# Garden: development notes

A node-graph control room for AI CLI sessions. Windows 11, personal use only.

This file tracks what is actually built, as against what was intended. Where the two differ it
says so rather than quietly describing the plan.

## Running it

There is a `Garden` shortcut on the Desktop. It runs `scripts/launch.ps1`, which starts both
processes if they are not already up, waits for the ports to answer, and opens the app in a
Chrome window with no tabs or address bar. Running it twice is safe: it reuses what is already
running. If exactly one half is up, it says so and stops rather than colliding on the held port.

By hand, from the repo root:

```
npm install
npm run dev
```

That starts the backend on `http://127.0.0.1:5178` and the UI on `http://127.0.0.1:5177`.
An Electron shell comes later; it is deliberately not a prerequisite, because the backend is a
separate plain Node process either way.

Health check: `curl http://127.0.0.1:5178/health`

Note that Vite is pinned to `host: '127.0.0.1'`. Its default bound `[::1]` only on this machine,
so anything probing IPv4 concluded the UI had not started. That cost a confusing 90-second
timeout in the launcher before it was found.

The Desktop icon is generated by `scripts/make-icon.py`, which draws it with no image library
because Pillow is not installed here.

## Architecture

```
packages/shared   types + the WebSocket protocol, shared by both sides
server/           plain Node. Owns every PTY, the SQLite store, and the command boundary
apps/web          React + Vite + @xyflow/react canvas + @xterm/xterm terminals
scripts/          capture.mjs, the screenshot harness
```

The backend runs as an ordinary Node process rather than inside Electron. That is a deliberate
choice: `node-pty` is a native module, and keeping it in plain Node means it never needs
rebuilding against Electron's ABI.

**The command boundary.** The renderer never names an executable. It sends a project id, a
profile id and an adapter id, and `server/src/adapters.ts` resolves those into a command line.
This is why terminal output can never cause a command to run.

## Decisions already settled

**Electron, not Tauri.** Tauri needs a Rust toolchain even for its Node-sidecar pattern, and
there is no `rustc`/`cargo` on this machine. Electron needs only Node and npm.

**`node-pty` 1.1.0 works here with no compiler.** It ships `prebuilds/win32-x64/pty.node` and
loads it directly, so Visual Studio Build Tools are not required. Verified by spawning a real
PowerShell session and reading back ANSI-coloured output. If a future Node major breaks that,
the fallback is `@lydell/node-pty`, which never invokes `node-gyp`.

**npm 11 blocks install scripts.** Native packages need an `allowScripts` entry in the ROOT
`package.json` (a workspace-level entry is ignored, with a warning).

**Terminals never live inside the canvas transform.** xterm.js computes mouse-to-cell position
from raw client coordinates and is not scale-aware, so a CSS-scaled terminal selects the wrong
characters (xyflow#3231, xyflow#3282). It is also main-thread-bound and roughly 34MB per
instance at 5000-line scrollback (xterm.js#4379). So canvas nodes render a cheap text preview of
the same byte stream, and real terminals are mounted at 1:1 in the dock below.

**Terminals are pooled, not rebuilt.** `apps/web/src/terminal-pool.ts` keeps one xterm instance
per session outside React. Creating and disposing per mount both threw (xterm queues internal
work that fails if the instance disappears underneath it, which React StrictMode's double-mount
triggers reliably) and would have thrown away the buffer every time a pane closed. Instances are
capped at 8 and LRU-evicted; eviction only drops rendering, never the PTY.

**Output is sequenced.** Every `session.data` message carries a cumulative byte count, and the
scrollback snapshot carries the `seq` it was taken at. A terminal attaching late discards live
chunks already inside its snapshot, so reattaching never duplicates output.

**A card's own byte counter starts at -1, not 0.** The scrollback restored from disk for a session
with no live process is numbered `seq: 0`, because nothing is running to have emitted anything. The
preview's counter started at 0 as well, so the first snapshot after a restart matched the "already
exactly current, skip it" test and was discarded: every card came back blank and stayed blank until
the owner woke the session and made it print. The dock terminal started its counter at -1 and
restored correctly all along, which is why the miniature and the pane below it disagreed about
whether anything had ever happened. Caught from the owner's own description, not from a test:
"Garden resets puts everything back to clear state until i fully wake it up and message it". Now
covered by `scripts/test-card-remembers-after-restart.mjs`, which against the old code gets "no
terminal history kept for this run".

**Previews come from a real headless terminal, not a regex.** `apps/web/src/preview.ts` keeps a
`@xterm/headless` instance per session purely for its buffer. The first version stripped ANSI
escapes with a regex and appended the result, which a blind reviewer caught producing
`Get-ChildItemGet-ChildItem | Select-Ob...`: PowerShell's line editor repositions the cursor and
erases as it redraws, so append-after-strip duplicates text. Note that `@xterm/headless` 6.0.0
ships a `module` field pointing at a file not in the tarball, so `apps/web/vite.config.ts`
aliases it to the ESM build that is actually published.

**Document HTML is sanitized.** Markdown comes from repositories and the renderer holds a socket
that can start processes, so rendered HTML goes through DOMPurify before it is inserted. The
server independently refuses any path that escapes the project folder, resolving symlinks first.

## Built so far

**The board.** Infinite zoomable canvas (0.05 to 3), cards packed automatically until you move
one, cards that never overlap, drag any edge or corner to resize, double-click to expand and again
to come back, ctrl and the wheel to size a card's text, undo and redo on board edits.

**Sessions.** Real ConPTY processes launched in the project folder. Each card shows a live colour
miniature of its terminal, a terminal input line that writes straight to the PTY, the account it
runs as, and a context gauge (blank until the hook spine lands). Turn off, turn on, rename,
duplicate. Cards are durable: only right-click, Delete and a confirmation removes one.

**Documents.** Any text or image file in the project opens as a card. Text edits in place with an
unsaved marker, saves refused if the file changed underneath, and images served by card id.

**Tabs and accounts.** One tab per project, opened with the OS folder picker. Accounts come from
the owner's own `~/.claude-account-map.json`, are bound per CLI per project, and are enforced
server-side rather than suggested.

**The context web.** The bottom dot opens everything a session runs from, in labelled columns:
instructions, its own notes, research, settings, skills, agent definitions, hooks and guards. For
`C:\Work\App1.0` that is seven columns and about 110 files. Guards come from
`hooks/lib/registry.mjs`, not `settings.json`, which is why all 23 appear.

**Per-card memory.** `~/.garden/memory/<project>/<card>/` with `LESSONS.md` and `NOTES.md`, handed
to the session as `GARDEN_MEMORY_DIR`, keyed by the card so it survives restarts.

**Wires.** Drawn by dragging, curved around obstacles, arrowheads for direction, four kinds
(manual, derived, blind, context) drawn differently. Tree arrangement plus four sidebar
arrangement presets.

## The hook spine

Garden writes its own settings file at `~/.garden/hooks/settings.json`, holding nothing but its
observer hooks, and hands it to every CLI it launches with `--settings`. That flag merges with
the other settings layers rather than replacing them, so the 23 guards dispatched from
`hooks/lib/registry.mjs` and the account check keep running untouched. Nothing is written into
`~/.claude/settings.json`, and uninstalling Garden removes every trace of this.

`server/hooks/garden-hook.mjs` runs inside the CLI's process on each event. It posts the payload
to a loopback receiver and exits 0 with `{}` on stdout no matter what happens, including a dead
server, a wrong port or a refused connection. An observer that can wedge a terminal would be
worse than no observer.

Attribution never guesses. `GARDEN_SESSION_ID` is set when Garden spawns the shell and is
inherited by the CLI and by every hook it runs, so an event finds its card without matching on
pids or working directories. Two cards open on the same folder is the normal case here, and
nothing matched on cwd could tell them apart.

What the spine produces:

- **Status the CLI actually reported.** A launched card says idle, not working: a live process
  says nothing about whether the CLI inside it is busy or sitting on a permission prompt. Hooks
  give the transition instantly, and `<config dir>/sessions/<pid>.json` is the authority on the
  current state, including `waitingFor` naming what a waiting session wants.
- **Subagent cards, created on dispatch and never deleted.** Named from the Agent call, coloured
  by role, wired to the parent with a `derived` wire that pulses when the dispatch fires, and
  still there holding its transcript after the agent exits.
- **Turns, recorded.** What was asked, whether the owner or another agent asked it, how long it
  took and which files were written. The history web unfolds these above a card as one file per
  turn under `~/.garden/history/<session>/`.
- **Transcripts, readable.** `transcript.open` renders an agent's own conversation as a card,
  including the full paths of every image it opened, which is how a blind reviewer's screenshot
  becomes reachable from the card that reviewed it.
- **The context gauge**, filled from the last usage record in the session's own transcript.

**The gauge is usually blank, and that is correct.** The CLI publishes token counts in its
transcript and nowhere else Garden can reach, and an interactive session's transcript is not on
disk when the turn ends: measured across three live runs, the path the CLI itself reported still
did not exist seventy seconds after `Stop`. Garden re-reads it every twenty seconds for as long as
a session is alive, so the gauge fills once that file appears, and stays blank until then rather
than showing an estimate. A model whose window size is unknown also leaves it blank rather than
assuming 200k.

There is one way to make it live, not yet taken because it has a cost: Claude Code's `statusLine`
command receives context usage on stdin, and Garden already installs a settings file it could add
one to. Doing that would replace the owner's own statusline inside Garden-launched sessions, which
is his call to make rather than a default to slip in.

Wires carry something. Each session owns `~/.garden/mail/<id>/`, handed over as
`GARDEN_MAIL_DIR`, holding `PEERS.md` (who it is wired to, rewritten whole so a deleted wire
disappears) and `INBOX.md` (appended, never rewritten). `wire.send` posts a message and lights
the wire. Nothing is injected into a prompt: an agent reads its mailbox when it chooses to, so a
wire can never hijack a running turn.

## How a spawned team lays itself out

The rule is about reading a team at a glance rather than following wires. Whoever dispatched sits
to the left, whoever was dispatched sits to the right, and each step down the chain steps down the
board, so seniority reads left to right and depth reads top to bottom. Siblings stack in a column
beside their maker rather than fanning out. The placement is still passed through the no-overlap
check, because a card placed exactly where the hierarchy wants it, on top of another card, hides
the thing it was drawn to show.

A spawn wire carries an arrowhead at both ends. A dispatch is a round trip: work goes out and the
answer comes back, and the answer coming home is the reason the card is kept at all. It is one
wire with two heads rather than two lines between the same pair of cards.

Connection points have one meaning each and never share an edge. Bottom is the files a session
runs from, top is its history, left and right are connections to other sessions and agents.

Verified by `scripts/test-spawn-topology.mjs`, which checks coordinates rather than trusting that
a wire exists.

## Every card learns its own job

Each card owns a directory under `~/.garden/memory/<project>/<title>-<id>`, handed to the session
as `GARDEN_MEMORY_DIR` and shown in the memory column of its file web. It holds `LESSONS.md`
(corrections), `NOTES.md` (the current picture) and `PLAYBOOK.md` (the procedure this card has
worked out for its own spot in the project).

Three things make it retention rather than scratch space. It is keyed to the card and not the
process, so it survives being turned off and on. Renaming a card keeps its directory, because the
id suffix is the real key and the title is only there to make the folder readable. And spawned
agents get one too, so an agent that has done the same job forty times in this project starts from
what it worked out the last thirty-nine.

Nothing is ever deleted for being finished. A card that has stopped goes idle and keeps its
position, its wires, its history and its memory until the owner explicitly deletes it.

**One honest limit.** Garden can only instrument sessions it launched. A session started in an
outside terminal can be read but never hooked, and Codex has no hook spine at all, so those cards
draw as unmonitored.

## What a run actually did

`server/src/pipeline.ts` derives one entry per turn from the events already stored, with a stage
table: intake, canon, plan, dispatch, code, review, close. Three states and never two: reached
when evidence was found, not-reached only once a run is closed and its whole window held nothing,
and unknown while a run is still open, because silence during a turn means "not yet" rather than
"did not happen". Every stage carries its provenance and a literal reason when it is not reached.

Two places it refuses to help itself. A plan seen only as an `ExitPlanMode` call is marked
inferred rather than structured, because that is the agent's claim to have planned rather than
evidence a plan exists. And a review stage says a review command ran, never that a review passed.

`pipelineSummary(store, projectId)` counts how many runs in a project reached each stage. That
number is the argument the owner actually wanted: eleven requests this week, blind review fired on
three.

## Transcripts are copied before they expire

The CLI deletes subagent transcripts after thirty days. `server/src/archive.ts` walks
`~/.claude/projects` every six hours and copies anything new or grown into Garden's own
`transcripts` table. It stats files and only reads one whose size changed, so a repeat pass over
1300 files is cheap, and it opens the source tree read-only: the module imports nothing from
`node:fs` that can write.

## The org chart, and what is actually enforced

The chain the owner runs: he talks to the orchestrator and to nobody else unless he clicks into a
card. The orchestrator owns the canon and hires the boss. The boss hands departmental tasks to
managers and is the only role that calls a reviewer. Managers hire their specialists and talk with
them until the work is done. Specialists do the work.

`ROLE_POWERS` in `server/src/hooks-install.ts` is the one table that decides what each role may
reach for, and everything else reads it: the deny list written into the session's settings file,
the brief written to `POWERS.md`, and the role validation on the server. There were two lists in
two files and they had already drifted.

| Role | Denied | Kept, and why |
| --- | --- | --- |
| orchestrator | Edit, MultiEdit, NotebookEdit, Bash | Write, since canon is authored whole. Agent, to hire the boss |
| boss | Write, Edit, MultiEdit, NotebookEdit | Bash, because the test suite is its job. Agent, for managers and reviewers |
| manager | Edit, MultiEdit, NotebookEdit, Bash | Write, for plans and work orders. Agent, for its specialists |
| worker | Agent and the team tools | Everything that does the work |
| reviewer | every writing tool, Bash, Agent, team tools | Reading, which is the whole job |

**Bash is the entry that matters.** A card denied Write and Edit can still write a file through a
shell, so a role with no sanctioned way to put bytes on disk loses Bash too. Garden shipped a brief
telling every manager that the editing tools were denied "so the only way you can change anything
is to hire someone who can" while Bash was open, which was false for every card that read it. Every
brief now prints its deny list verbatim so the claim and the file cannot drift again.

**A role must be set at creation.** The CLI reads permissions once, at launch, so a card created
and then given a role ran its whole first session with none of that role's denials. `session.create`
carries the role, the model, the effort, the helper cap and who it answers to, draws the reporting
wire before launching, and can create a card switched off so a blueprint can be laid out before
anything costs a token.

## Agents hand work along a wire

`server/bin/garden-send.mjs` is handed to every session as `GARDEN_SEND`. Running it posts to
`POST /mail`, which appends to the target's inbox and records the delivery. Before this, deliveries
only arrived over the WebSocket, so only the owner's hands could send one and a manager had no way
to give its worker anything: the chain was drawn and could not be walked.

The wire is the permission. A worker trying to report straight to the orchestrator is refused and
told which wire is missing, and the refusal is recorded, because an agent trying to go somewhere
the chain forbids is worth seeing. Who is sending comes from `GARDEN_SESSION_ID`, the same thread
the hook spine runs on: an agent that deliberately overrode it could lie, which is stated rather
than pretended away.

**One review round, then it goes to the owner.** `server/src/tasks.ts` counts review hand-offs for a
task id and refuses a second round, and refuses remediation back down after one, telling the boss to
send it up instead. When a task reaches the orchestrator, Garden writes the report the owner asked
for beside that card: what was reported done, the reviewer's notes, the files actually written taken
from the CLI's own tool calls, and the full trail. There is no verdict line, and there will not be
one.

## Your layout cannot be lost to a button press

A snapshot is taken on the server before every arrangement, one per project, always overwritten, so
Previous survives a reload, a restart and another window. Layouts can be saved by name, and each of
the four styles keeps the version the owner edited from it, so a style offers both the clean shape
and his own. Verified by a test that reconnects as a fresh client before restoring.

## One card creates, everything else asks

`server/bin/garden-hire.mjs` is handed to every session as `GARDEN_HIRE`, and `POWERS.md` prints the
exact command, because a capability nobody is told about is the same as one that does not exist: the
send shim spent a while working and unused for precisely that reason.

Only a card whose role has `creates` may bring a card into being, which is the `operator` and
nothing else. Every other card's request is filed as real mail to the operator and answered along a
wire, drawing one if there is not one already. Mail rather than a queue table, because Garden never
injects into a prompt and the mailbox is the only thing that already makes a card look at something.

The roots go on stdin and are required. A card hired without them reads only the project's
instructions and the machine's, and answers as whatever those describe rather than as the thing it
was hired to be, which is the whole complaint about cards inheriting everything. They are written
into the new card's own `CLAUDE.md` below the marker Garden maintains, so Garden's half stays
accurate and the hirer's half is never overwritten.

Cards are created switched off. Laying one out costs nothing and starting it is a separate decision
with its own line in the ceiling, so hiring can never quietly spend a context window.

## The board has a size, and it is somebody's decision

`BoardLimits` is three counts per project, in SQLite, changed while the board is running through
`limits.get` and `limits.set`: how many cards may exist, how many may run at once, and how many may
answer to one card. That last one is the first time a parent's own `teamSize` is read at all; it was
written onto every card at creation and never consulted, so a manager told to keep two helpers
brought up six and nothing refused.

Enforced inside the `session.create` handler rather than only at the hiring endpoint, so a scratch
script sending raw WebSocket frames meets the same refusal an agent does, the owner's own right-click
included. A ceiling with an exception for whoever is most likely to be in a hurry is not a ceiling.

Lowering a limit below what is already on the board is allowed and does nothing retroactive. Every
refusal names the count and the figure, and is recorded as a `hire.refused` event against the card
that asked, so attempts are visible rather than merely blocked.

The reason this exists: one request produced thirty-eight cards with twenty sessions running, and no
card had misbehaved. Each hired what its brief allowed. The total was nobody's decision.

## Loops: a prompt typed into a card every N minutes, switched from the rail

Owner, 2026-09-11: *"create loop section in the ceiling menus that allows me to toggle loops on/off
and select frequency of checking in minutes."* Before this the only loop on the board was a timer
inside the orchestrator's own session, which the board could neither see nor stop.

A loop is one row in the `loops` table: card, prompt, minutes, on or off (`CardLoop` in shared).
The rail's Loops section, under Ceiling, is where the owner sets all four; `garden-loop.mjs` sets
the same four from a terminal. The server checks every twenty seconds and types the prompt, then
Enter, into the card only when its status is `idle`; a card that is working, waiting, stopped or
closed is left alone and the loop's `lastOutcome` says `held: card working` and so on, so a loop
that is not firing never reads as silence. Switching a loop on starts its clock, so "every 15
minutes" means the first one in 15 minutes. Nothing about a loop is inferred: what shows on the
row is the server's own record of the last time the loop was due.

## What is NOT built
- The worker cycle: write the notes, check the record exists, then clear the context. The gate is
  designed in the plan and not built.
- A view for the pipeline. The stages are derived and reachable as `pipeline.get`, and nothing
  draws them.
- Blueprint slots that a live session binds into.
- Minimising an already-collapsed web card should fold it into the blip.

## Tests

Run the lot with `node scripts/run-suite.mjs`, one at a time, after `npm run build`. Three tests
launch a real CLI and spend real tokens; they are held back unless `--paid` is passed, and they are
named in the summary either way, because an unmentioned omission reads exactly like a pass.

**Every test gets a Garden of its own.** Its own free port, its own workspace, its own database, via
`scripts/lib/instance.mjs`, and for the browser tests `scripts/lib/board.mjs`, which also seeds a
known board and serves the built app off that same port.

That is not tidiness. Every one of these scripts used to open with
`Number(process.env.GARDEN_PORT) || 5178`, so running one with no environment set pointed it at the
board the owner was working on. It has now cost him three times: twice badly enough that the damage
got blamed on the app rather than on the script, and once during the session that fixed it, adding
three projects and six cards to a live board and leaving shell processes running inside his other
repo. `scripts/lib/target.mjs` inverts the default: no port in the environment means a Garden of its
own, and reaching his board takes `GARDEN_PORT=5178` or `GARDEN_LIVE=1`, said out loud.

The same trap has a second half worth knowing: a test that opens `new Store()` with no argument gets
the DEFAULT database, which is his, no matter which server it is posting to. Pass the instance's
path.

Individually, each creates what it needs and cleans up after itself.

## Capture is headless on purpose

`scripts/capture.mjs` drives the installed Chrome with no visible window, so a review pass never
steals the screen. That also means the owner sees nothing happen: the evidence is the PNGs in
`docs/shots/`, and they are the thing to open.

This is a live argument for a Garden feature. When a blind reviewer opens a screenshot, its
transcript records an `attachment` record next to the `tool_use`. So the subagent conversation
view should render those images inline, in order, showing what the agent actually looked at
rather than only what it concluded. Same for any agent that reads an image.

The path comes free with it. A `Read` tool_use block carries the literal absolute `file_path` in
its input, so the view can show the thumbnail, the full path as copyable text, and open-on-click
without parsing anything. This is structured data, not inference.

## The rule that overrides convenience: cards are never lost

A card is a durable object and the process behind it is not. Turning a session off ends the
process and leaves the card, its position and its history exactly where they were. Only
right-click, Delete, and a confirmation removes anything, and nothing in the server deletes a
session row on any other path.

This is enforced by `scripts/test-lifecycle.mjs`, which drives the real WebSocket and then checks
SQLite directly. It exists because the first version deleted the row while the screen still looked
fine, so a UI-only check would have passed.

Two traps found while building it. Killing a PTY returns a non-zero exit code, so a deliberate
turn-off looked identical to a crash until the manager started recording that Garden asked for the
exit. And React Flow emits position changes for its own reasons, including measurement and
fitView, so persisting all of them marked every card as hand-positioned at meaningless
coordinates; auto-packing switched itself off and cards overlapped badly enough that one card's
heading sat on top of another card's buttons. Only `onNodeDragStop` counts as the owner placing a
card.

## The smeared, doubled text was Windows, and one flag stopped it

The owner had been living with text drawn twice at two horizontal offsets, on top of itself, and
reported it happening in raw terminals as well as in Garden. That second fact sent the first
investigation the wrong way: it was read as "not Garden's problem" when the truth is that both are
the same Microsoft bug and Garden was pulling its trigger far more often than a terminal window does.

**What it is.** Windows' in-box ConPTY re-emits its whole screen buffer when it is resized, and
alternate-screen buffers of different sizes confuse it outright
([microsoft/terminal#4389](https://github.com/microsoft/terminal/issues/4389), open since January
2020, Backlog, no PR). A full-screen alt-screen TUI is the worst case, which is exactly what Claude
Code is. In a terminal window you hit it when you drag the window. In Garden you hit it when you open
a second pane, drag any panel handle, collapse the sidebar, or start or stop a session.

**Measured, not argued.** `scripts/test-conpty-reflow.mjs` runs `scripts/lib/alt-screen-tui.mjs`, a
fixture that takes over the screen, draws a box, and stamps every line it writes with the number of
the paint that drew it. Node does not raise `resize` on Windows under ConPTY, so the fixture paints
exactly once, which makes the arithmetic unambiguous: whatever else is in the stream, nobody sent it.
Six resizes, in-box ConPTY: **six copies**, one per resize. With `useConptyDll: true`, which uses the
conpty.dll 1.23.2510.08001 that node-pty ships instead of the one in Windows: **zero**, across three
runs. `IPty.clear()`, which node-pty documents as the way "to avoid ConPTY possibly reprinting the
screen", changed nothing: still six. `GARDEN_CONPTY_DLL=0` goes back to Windows' copy, and the test
shows six again, so the flag is verified in both directions.

**The second half was Garden's own.** Every process spawns at 120x30 and the pane corrects it once,
and that correction is deduped on the client against the last size sent. Stop a card and start it
again and the pane has not changed, so the dedupe swallowed the message and the replacement process
spent its life believing it had 120 columns while the pane drew it at 260. Measured exactly that:
`120x30` against a pane drawing `260x25`. Nothing reported it because both halves were internally
consistent and only disagreed with each other. `forgetReportedSize` in `state.ts` clears the memory
whenever a card's pid changes, and `scripts/test-restarted-card-knows-its-size.mjs` is red without it.

**One thing that turned out not to be a problem, and was going to be a week of work.** The 256 KB
scrollback is labelled with one geometry while holding bytes drawn at several, so replaying it into
one terminal looked certain to smear, and the plan was to cut the buffer into segments and resize
between them on replay. `scripts/test-replay-across-resize.mjs` builds exactly that buffer on
purpose, wide screen then narrow screen, replays it through the same headless xterm a card uses, and
the final screen carries one paint and no fragments of the other. A full-screen program repaints
everything after a resize and that repaint lands last. Not built.

## Why the board used to freeze

Four separate things, found together while chasing one complaint ("windows in the app frequently
freeze and terminals stop updating text"). None of them was the resize theory the hunt started from.
Recorded because each one looked fine in the diff and only showed up when something was measured.

**A pane on screen could be disposed to make room for another.** The pool caps xterm instances at
eight and evicts by `lastUsed`, which was stamped once, when a pane mounted, and eviction did not
check whether the instance was still displayed. Keep one pane open while opening and closing eight
others, which is the ordinary shape of watching an orchestrator while cycling through workers, and
the ninth killed the first: unsubscribed from the byte stream, xterm disposed, host removed from the
DOM. No error anywhere. `evictIfNeeded` now skips any entry with a live mount, `Terminal.tsx`
registers and releases that mount, and `lastUsed` is refreshed by arriving bytes so recency means
activity. `scripts/test-pane-stays-live.mjs` runs that exact sequence; against the old code the
pinned pane comes back with no `.xterm-rows` at all.

**Nothing noticed a socket that died without saying so.** Reconnecting hung entirely off `onclose`,
and a half-open TCP connection never fires it, which is what a sleep/resume leaves behind. Both ends
report OPEN forever, sends succeed into nothing, and every card stops at the same instant while the
page still says connected. The page now sends a `pulse` every five seconds and the server answers
it; twenty seconds of silence and the page abandons the socket. Two details cost time. A
protocol-level WebSocket ping is answered by the browser below JavaScript and never reaches the
page, so it cannot be used for this, which is why `pulse` exists in the protocol at all. And
`close()` waits for a close handshake from the peer that has stopped talking, so `giveUp` detaches
the handlers and announces the disconnect itself rather than waiting; before that, a black-holed
connection did not surface within thirty seconds. A handshake that never completes is abandoned
after eight seconds too, or the board never comes back once it is stuck CONNECTING.

**The server sliced a 256 KB string on every PTY chunk.** Once the scrollback buffer was full,
every chunk a CLI emitted, hundreds a second while it draws, copied the whole quarter-megabyte. The
buffer now runs half again over the limit before being trimmed back, and `capped()` is what anything
outside the module is handed. Twenty thousand chunks against a full buffer: 1744 ms of blocking
before, 8 ms after.

**Two more theories that measurement did not support, kept here because they read as obviously true
and were not.** `WireEdge` calling `useNodes()` inside its routing memo works out to tens of
thousands of rectangle tests per pointermove on paper; forty cards and thirty-nine wires dragged
through a hundred and fifty pointer moves blocked the main thread for zero milliseconds across zero
long tasks, on the old code. And the once-a-second token scan over every live session's whole
scrollback measures about 0.10 ms per 256 KB, so ten live cards cost about a millisecond a second.
Both changes were kept, because doing less work for the same result is still right, but neither is a
fix for anything the owner felt, and the completion note said so. The arithmetic-looks-expensive
argument is not evidence; the only one of the four that survived being measured was the string
slice above.

`scripts/test-socket-liveness.mjs` puts a TCP relay in front of the server and stops it forwarding
without closing anything, which is the only way to produce the case that actually bites. A clean
shutdown does not test it: that fires `onclose`, which always worked.

**The watchdog then invented a disconnection of its own, and the owner hit it the same day.** Chrome
throttles timers in a window that is minimised or behind another one, down to about once a minute. So
the heartbeat stops going out, nothing comes back, and the next time the timer runs the clock shows a
minute of silence against a twenty second limit. It closed a healthy socket and put "Not connected to
the Garden server" on screen, on a server that was up and answering throughout, and on a quiet board
it did it again on every wake-up because the only traffic was the heartbeat it had stopped sending.
The guard is that a gap between ticks far longer than the interval means the timer was throttled
rather than the socket being silent, so the clock is reset instead of believed.

**The test for it had to count sockets, not look at the banner.** The first version sampled whether
the offline banner was on screen and passed against the broken build, because the reconnect is fast
enough that the banner comes and goes between checks. What the owner sees is that flicker repeating,
so what has to be measured is how many times the page threw its connection away. Against the broken
build: three extra sockets for three gaps. Fixed: zero.

## Known issues

- A favicon request 404s. Cosmetic only.
- Profiles are modelled and scoped in the adapters but there is no UI to create them yet, so
  every session currently runs on the default account.
- `session.move` is persisted but not echoed to other clients, so two browser windows would
  disagree about node positions. Single-window use is unaffected.
- Restarting the app cannot re-parent a Windows process, so every session is marked exited on
  boot. That is honest rather than fixable.
- `useConptyDll` is marked experimental by node-pty, and Garden now turns it on for every session
  because it is the only thing that stopped the doubled text. `GARDEN_CONPTY_DLL=0` goes back to
  Windows' own copy. Worth knowing about if a session ever misbehaves in a way that is new.

## What the blind passes have caught so far

Worth recording, because it is the argument for keeping the practice rather than trusting a
completion summary:

- Typing into a terminal did nothing. Keystrokes went to the last-clicked button, so the pane
  toggled shut instead of running a command. The screenshot showed an empty prompt where a
  command should have been.
- Preview text was garbled, showing `Get-ChildItemGet-ChildItem | Select-Ob...`, which exposed
  the regex-over-ANSI mistake behind it.
- Card text at 11.5px was called near-illegible on a 4K display.
- Cards clustered into a corner of a very wide screen, which led to the packing rewrite.
- The conversation toggle swapped its icon for a different one when pressed, and a reviewer could
  not tell what the replacement meant or whether pressing it again was the way back.
- Two further passes on the replacement: an emoji filled with the accent colour read as "a solid
  glossy violet orb" with no glyph, and even unfilled it would not resolve into a shape at eleven
  pixels. **An emoji is not an icon at card-header size**, and it cannot be recoloured to fit its
  background. It is a word now.
- The toggle was offered on a Shell card, where the conversation can only ever be empty. The
  reviewer read its copy about a CLI naming a transcript as text written for something else and
  reused here, which is exactly what it was.

None of these were visible from reading the diff, and the first one would have shipped as
"terminal working" on the strength of the code looking correct.

## Each card keeps its own lessons

A card gets a notes directory at `~/.garden/memory/<project>/<card>/`, holding `LESSONS.md` and
`NOTES.md`, and the session is handed the path as `GARDEN_MEMORY_DIR` along with `GARDEN_CARD`
and `GARDEN_PROJECT`. Plain files at a stable absolute path, so the agent reads and writes them
with the tools it already has and Garden brokers nothing.

Keyed by the **card**, not the session. A session id changes every time it is turned on, so
lessons keyed to it would reset constantly, which is the opposite of retention. Seeding never
overwrites: what accumulated last time is the point.

Both files appear in that card's bottom web alongside everything else it runs from, and the web
now marks what is **always** in play (instructions, this card's own notes, guards, which fire on
every matching hook event) against what is only **sometimes** used (skills and agent definitions,
which do nothing until something invokes them). Listing all of them as equals would overstate
what actually shapes a session.

## What a card knows before it does anything

A card used to load the project's `CLAUDE.md`, the user's, and every other one between its working
directory and the filesystem root. Every card is spawned in the project root, so every card on a
board got the same instructions, and the owner's summary was "each claude session gets every .md ever
created". Worse, the one file written for that card, its own `CLAUDE.md` in its memory directory, was
never loaded at all, because a memory directory is not on that path. So each card had everyone's
instructions and none of its own.

**Turning it all off was step one and was too much on its own.** `claudeMdExcludes` in the per-card
settings file removes the shared instruction files, and `autoMemoryEnabled: false` removes the CLI's
own auto-memory, which defaults to a directory keyed to the working directory that every card shares.
Both were verified against claude 2.1.232 rather than assumed: asked to list its loaded instruction
files, a plain run named `~/.claude/CLAUDE.md` and `C:\Garden\CLAUDE.md`; the same run with these
settings answered `NONE`. The auto-memory half was only found because that first answer volunteered
it, which is the argument for asking a real session instead of reading a settings reference.

**Three tiers, general to specific.** The owner's words on why: "i want them to have discrete roots
for their roles is main thing to help with focus/context improved results instead of so many general
agent cards".

- `~/.garden/roots/ALL.md`, every card. How to write, what may never be claimed, what not to touch.
- `~/.garden/roots/roles/<role>.md`, every card of that role. What this kind of card is for.
- The card's own `CLAUDE.md`, written by whoever made it.

Seeded once and never overwritten, plain files, listed in the card's own context web so they can be
opened and edited on the board. They reach a session through the `SessionStart` hook, which is the
CLI's supported door for adding context. Not as `CLAUDE.md` files, and not through `--add-dir`
either: a directory added that way contributed nothing to a session's instructions when measured.

**Each section of the startup brief has its own budget.** Past ten thousand characters the CLI spills
hook output to a file and leaves a preview and a path, so a brief that grows stops being a brief
without anything failing. One shared cap at the end would have meant adding a tier above the card's
brief silently ate the card's brief. A section that does not fit says so and names its file.

**Two bugs found on the way.** Roots were only stored for a card created switched off, so a card
created and started in one call had its creator's brief accepted and then discarded. And roots could
only arrive through `POST /hire`, so an agent could give a card a brief and the owner making one by
hand could not; `session.create` carries them now and the new-card form has a Brief box above the
fold, since it is the only thing a card knows.

## The roots dot opens columns, not a hundred cards

Pressing the bottom dot used to put every file a card runs from on the board at once. On a real card
that is well over a hundred nodes arriving together, and the owner's report was the plain one: "makes
it too laggy the way it is right now".

It now unfolds one pill per column, each carrying the count that would have arrived as cards, and a
column opens its own files when it is pressed. Nothing is hidden: the counts say how many are behind
each one, which is the question the web exists to answer, and the files are one click further rather
than unavailable. Measured on a board with 44 files across five groups: five nodes instead of
forty-four.

The columns are a view and not a fact, so they live in the client and nothing is written anywhere.
The server already accepted `context.open` for a single group; only the dot had to stop asking for
everything. A group that already has files open is drawn by the existing header, which is derived
from where its cards actually are, so a header is never drawn twice for one column.

`scripts/test-roots-open-as-columns.mjs` counts nodes, because "laggy" is not something a test can
feel and the number arriving in one go is what was wrong.

## A card can show its conversation instead of its terminal

A session card had one body: a miniature of its terminal. That is a picture of drawing instructions,
capped at 256 KB, thrown away by every restart, and unreadable the moment a full-screen CLI takes the
screen over. Garden already read the CLI's own transcript into `ChatTurn[]` of `asked` / `said` /
`did`, and already rendered it, but only on subagent cards, so the cards the owner actually works
with had no readable record of what was said at all.

`bodyView` on the session row is now `terminal` or `chat`, with a toggle in the card header and the
same toggle in the dock pane, so the 1:1 view can show a conversation too. It is stored rather than
held in the browser, for the same reason a card's size and colour are: it survives a reload and
reaches a second window. Null means nobody has chosen, and the default is the card's kind, so a
subagent card still opens on its conversation and a session card still opens on its terminal.

**Only a Claude card gets the switch**, and that came out of the blind pass. The first version put it
on every session card, and a reviewer shown a Shell card in the conversation state read the copy
about a CLI naming a transcript file as text written for something else and reused here. It was: a
shell has no transcript and never will, so the control had one working position. That is the same
reasoning already applied to what a role may reach for, where something a card would only discover it
cannot do at the moment of refusal is worse than not offering it.

The control itself took three blind passes to get right, which is worth recording because none of it
was visible from the code. It started as an icon that swapped for a second icon when pressed, and the
reviewer could not tell what the replacement meant or whether pressing it again was the way back. It
became one speech bubble that filled with the accent colour when on, and the next reviewer described
"a solid glossy violet orb" with no glyph in it: an emoji carries its own colours, so a text colour
does nothing to it and a saturated fill simply swallows it. The fill became a ring, and the third
reviewer could see it was on and expected a second press to undo it, but still could not resolve the
shape inside: at the eleven pixels a card header runs, an emoji has no internal detail left. So it is
the word `chat`, which is the same thing the header does two controls along with `off`.

Durability is the point, and it comes from where the data lives. The turns are read from the
transcript file, so they outlast the process, the card being turned off, and the app restarting, none
of which the terminal buffer does. `Ingest.pushChat` broadcasts them when the `Stop` hook fires,
twice for the same reason `readUsage` is called twice there, and skips the read entirely when the
file has not grown.

The three empty states are kept apart on purpose: an answer that has not arrived, a transcript with
no turns in it, and a card the CLI never named a transcript for. Drawing all three as one blank pane
is how a card ends up implying a run did nothing.

**It has to survive a long session, and the first version did not.** `readChat` read the whole
transcript with `readFileSync` to keep the last sixty turns. Measured against a real 120 MB
transcript on this machine: 785 ms and 344 MB resident, on the same thread that reads every PTY and
serves every socket, called twice at the end of every turn. A card in a long-running session would
have stalled the whole board for the best part of two seconds each time it finished thinking. It
reads a four megabyte tail now, growing the window when that did not hold enough turns and stopping
at 32 MB. Same file: 15 ms. The one transcript here that averages four hundred kilobytes a record
takes 141 ms to find 56 turns, which is the worst case measured.

**Test it full, not just empty.** The first test of this proved the toggle, the storage and the pane,
and every one of its assertions was satisfied by the message that says there is nothing to show,
because its card had never run. A view only ever tested empty is a view nobody has checked.
`scripts/test-conversation-shows-real-turns.mjs` hands a card a real Claude transcript through the
`/hook` endpoint, the same way a live one arrives, and reads the words back off the card: 60 turns,
all with text, labelled Asked, Said and Did. The transcript is a copy taken read-only into the test's
own temp directory, because a synthetic one would only prove Garden agrees with my idea of the
format, and pointing at the original would put a real conversation one bug away from being written
to.

## Editing files on the board

A document card edits in place as plain text and writes back to disk, with an unsaved marker and
a brief saved confirmation, because a save with no feedback leaves you unsure it wrote anything.
Ctrl+S saves, Escape cancels. This covers the settings files too: a card's own settings live in
its bottom web, so changing what a session runs from is done on the board rather than by hunting
through folders.

`scripts/test-doc-edit.mjs` proves a save reaches disk for a file inside the project and that the
renderer cannot name an absolute path to reach one outside it. Files outside the project are
readable and writable only through cards the server itself created from its own scan.

## Webs open into empty canvas

`findFreeArea` in the server walks down and then outward from the owning card, taking the first
placement where the whole block clears every existing card. The canvas is infinite, so there is
never a reason to drop 68 cards on top of the board. `scripts/test-free-space.mjs` checks every
web card against every other card for overlap.

## Why the board is cheaper than one long session

The owner's own reason for wanting this, and it should drive the design rather than be a nice
side effect. One long session re-sends its entire history on every turn, so the cost of a task
grows with everything that came before it. The same work split across cards means each session
carries only its own narrow context.

Two consequences for Garden. History is one file per piece of work rather than one long log,
so a later agent reads the two entries it needs instead of inheriting the whole story. And a
wire hands over a path, not a transcript: the receiving agent reads what it needs on demand.

Anything that quietly re-injects a lot of context into a session works against the only reason
this app is worth using.

## Decided, not yet built: a wire has to tell the agent it exists

Drawing a wire from a Blender MCP session to the project's main agent should make the main agent
aware it can hand Blender work over. That does not happen for free: an agent cannot see the
canvas, so a line on screen means nothing to it until something tells it.

A wire between two session cards therefore does three things:

- **Records the connection** in Garden, which is what the board draws.
- **Opens a channel.** Each session gets a mailbox at `~/.garden/mail/<sessionId>/`, mirroring the
  `.claude/mail/` convention already used in `C:\Work\App\1.0`. A file path is a channel both
  ends can use with the tools they already have, with no new protocol to invent.
- **Announces it.** Garden stages a short message into the other session's prompt naming the new
  connection, what it is for, and the exact mailbox path. It is staged, not sent: you confirm it,
  because injecting text into a running agent behind your back is exactly the kind of invisible
  action this app exists to remove.

The label on the wire is what the announcement says the connection is for, which is why wires are
labellable. An unlabelled wire announces the connection and nothing more.

## Decided, not yet built: an orchestrator per blueprint

Each blueprint gets one specialised orchestrator agent that owns it. It talks only to the owner: it plans,
writes the blueprint, and proposes work, but does not do the work itself. That restriction is
enforced by the tools its definition grants, not by asking it politely, so it cannot quietly start
editing the repo.

Three mechanisms make this real rather than decorative:

- **It is an ordinary session card**, launched with its own agent definition and wired as the root
  of the blueprint. No special runtime.
- **It builds blueprints by writing a file.** Garden watches `~/.garden/blueprints/` and
  materialises cards and wires from what appears there. The agent writes, Garden reads. Nothing is
  brokered through an invented API, which means the same file is editable by hand.
- **Dispatches are proposed, not executed.** A `PreToolUse` hook on the `Agent` tool can return a
  permission decision, so Garden can show an intended subagent as a greyed proposed card, already
  wired into position, and hold it until the owner approves or rejects. That is the moderation
  point: nothing gets hired without being seen first.

The hook has to block while it waits for an answer, so it needs a timeout and a fail-open default.
A forgotten approval prompt must never leave a session frozen with no explanation.

## Decided, not yet built: cards summon cards

A card is not only something you create. When a session spawns a subagent or hires a team, each of
those gets its own card on the same board, following the same rules: durable, collapsible,
resizable, never auto-removed, with its own history above it and its own context below it. The
board grows as the work grows, which is the point.

Two consequences for the layout code. New cards must be placed **near their parent** rather than
appended to the end of the pack, or a team of five will scatter across the board away from the
session that hired them. And the packer must only ever place cards the owner has not positioned,
which the `manualPos` flag already guarantees.

## Decided, not yet built: the two attachment points

A card has two attachment points, and they mean opposite things. This symmetry is the design, not
a coincidence:

- **The dot below** is what the session runs *from*: its agent definition, the project and user
  `CLAUDE.md`, `AGENTS.md`, the settings layers in effect, the hooks and guards. Clicking it
  unfolds those as small file cards wired back to the dot.
- **The node above** is what the session *did*: its work history and what it is working on now.

The second one has a requirement the first does not. The point of storing history in a fixed place
is so you can ask a main agent "what was worked on" and it can go and read the other cards' notes
itself. That only works if the history is a real file on disk at a stable path, not a row in
Garden's database that only Garden can see.

So history is written to `~/.garden/history/<project>/<session>/` as plain markdown plus an
`INDEX.md`, mirroring the `agent-worklog` convention already used in `C:\Work\App\1.0`. An
absolute path there is readable by any agent with the Read tool, so "look through the other cards"
becomes an ordinary file read rather than a feature Garden has to broker. Writing into the user's
repo stays a button, never automatic, for the collision reasons in the plan.

**One file per piece of work**, so an audit trail is greppable rather than one long log. Each file
records, in this order:

- **What was asked.** The prompt text, from `UserPromptSubmit`.
- **Where the request came from.** That hook carries `source`, which is one of `user`, `sdk`,
  `system`, `loop_wakeup` or `schedule_wakeup`, and a subagent's own events carry `agent_id` and
  `agent_type`. So "you asked for this" versus "another agent asked for this" is a structured
  fact, not a guess, and the file says which.
- **What it actually did.** Tool calls from `PostToolUse`, files written, commands run, subagents
  dispatched, and the result.
- **Attachments.** When a step involved an image, such as a blind screenshot review, the entry is
  labelled as a review and records the absolute `file_path` from the `Read` tool call. The history
  card shows the thumbnail and opens the full image on double click, so you can see what the
  reviewer actually looked at rather than only its conclusion.

The top blip opens these as their own cards, wired back to the session, and collapses them away
again. Same for the bottom blip and the files the session runs from.
